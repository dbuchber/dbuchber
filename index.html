INFORMATICS · 2025

AI Agent Invoice Automation

Prototype for an AI agent-based automated invoice processing pipeline with direct SAP integration. Demonstrated at the 20th INFORMATICS SAPshots event alongside manufacturing and healthcare use cases.

Question How can LLM agents support structured invoice processing in enterprise SAP environments with and without human intervention?
Methods Invoices are exactly the documents an enterprise cannot send to a cloud model, so the question is whether a model running on the company’s own hardware is good enough to do the work. Agents parse the document, derive the posting and write it into SAP through its own API, with the boundary between what the agent completes alone and what a person still has to confirm treated as a design decision rather than a setting.
Outcome Built and validated a proof of concept for on-premise LLM and SAP integration as a viable enterprise architecture; presented publicly at SAPshots.

APA × WU Data Science Lab · 2025

Interview Detection & Search Optimisation

Developed with three fellow students — a two-stage AI system that identifies interviews within the APA news database and optimises search relevance. Trained exclusively on secure, private infrastructure.

Question Can a two-stage model reliably detect interview formats and improve relevance ranking across a large news archive?
Methods An interview is a format, not a subject — it has to be recognised from structure and turn-taking rather than from what the text is about, which is why detection and ranking are two stages instead of one classifier. The archive cannot leave the newsroom, so every training and evaluation run happened on APA’s own infrastructure rather than on rented compute.
Outcome Two-stage system improving both interview classification accuracy and search result relevance in the APA archive.

Architecture · 2026

Document Intelligence Architecture

An architecture concept for a document assistant used by a few thousand people on long, structured documents — contracts, legislation, briefs. Two problems drive the whole design: keeping cost and latency flat whether a workspace holds five documents or five hundred, and sharing a document set between people and between tools without inventing a second permission model for each.

Question Where do the load-bearing decisions in a retrieval system actually sit — and which of them are architecture rather than model choice?
Methods The workspace, not the user, as the organising unit, so sharing between people and sharing between tools become the same concept. Permissions held in the same database as the vectors, so the scope filter is a SQL predicate taken from the session and never from user or model input. Vendor abstractions pitched at document structure rather than domain semantics — pitched any higher, the interface becomes one provider’s feature set with the other faked by regex, which is the lock-in the abstraction exists to prevent. Provenance carried through ingestion so a citation resolves to a page and a clause, and a grounding check that marks unsupported claims rather than displaying them as grounded.
Outcome Seven abstraction layers, each earning its place through a second implementation that is actually run rather than anticipated — an abstraction with one implementation is a guess about the future. Every managed cloud service replaced locally by a container behind the same interface, so application code is identical in the proof of concept and in production. And a cost preview before large batch reviews, on the principle that a system which queues work has to say so before the user commits, not after.

SEREVO

Most venues run the floor on a radio and a laminated plan, and by half past nine the plan is already wrong: a spot assigned twice, a round of drinks delivered to the wrong row, two parasols that were in the inventory in May and are not on the floor in July. None of that is a booking problem — it happens in the hours after the booking, the part most hospitality software treats as somebody else’s job. Booking software ends at check-in; SEREVO starts there.

Question A beach club is not a restaurant with sand and a pool deck is not a dining room with chlorine — the floor plan changes with the season, staff are never standing at a terminal, guests will not install anything, and the stock walks away. What does an operations system look like when it is built for that, rather than for a fixed room with fixed tables?
Methods One product core serving several verticals instead of a codebase per venue type — beaches first as the go-to-market wedge, with pools, spas, resorts and hotels following the same pattern. Spots, orders, service requests, activities and inventory in a single live operational view; guests order by scanning once, with no app and no account. Existing PMS, POS, access control and messaging stay connected rather than being replaced, and multi-tenancy keeps each property’s team, brand and data separate under one management view.
Outcome Running multi-tenant in production. A self-service demo provisions a complete venue — zones, spots, loungers and parasols, a menu, checked-in guests and orders already in progress — in about thirty seconds, so the product is evaluated by being used rather than in a sales call. Every service request arrives with its location and an owner; equipment stays visible when it moves, needs repair or leaves service.
Multi-tenant Hospitality Ops Guest Experience Self-service Onboarding

fuxiq · Ongoing

AI Hedging

Most requests do not need the most expensive model. AI Hedging asks which share of a company’s LLM workload genuinely requires the frontier model, and what a controlled second path across cheaper, hosted and local inference actually costs and saves. The longer-term product is a European, multi-tenant AI router that picks the cheapest model still meeting each customer’s own quality bar, latency target and data policy.

Question Which share of an LLM workload actually needs the most expensive model — and what does a second path cost once verifier runs, escalations and additional failures are netted against the saving?
Methods The business case modelled end to end: avoided API cost netted against verifier and escalation runs, additional failures measured against the frontier reference, and — where selected — local total cost of ownership and reduced outage risk. The workload is split into easy, medium and hard classes as a transparent starting policy, explicitly not the target product’s decision logic. Sensitivity across price drift rather than a single number, with placeholder assumptions kept visibly separate from customer-measured values.
Outcome A business case whose actual result is the sensitivity, not a headline saving: at which price drift, task mix and quality bar a second path stops paying. A hosted second path cuts cost and provider concentration without CAPEX; own hardware is a separate scenario that only pays at sufficient load or with defensible outage value. The roadmap runs from the routing simulator through offline evaluation with design partners and a BYOK gateway to adaptive, tenant-isolated routing policies.
LLM Routing TCO Modelling Multi-tenant EU Data Residency Cost Optimisation

EveryWay

A route can work on the map and still be impassable in reality. A single broken lift is not a minor inconvenience — if it is the only step-free access to a station, the route does not get longer, it disappears. EveryWay plans journeys that already know the current state of the infrastructure and reroute around it before somebody is standing in front of the problem.

Question What does a routing system need to know — about the network’s current state and about the person travelling — before its shortest path is actually a usable path?
Methods Six combinable need profiles — step-free, vision, hearing, stamina, low-stimulus and simple routes — instead of one accessibility filter; static infrastructure from OpenStreetMap tagging joined with operator real-time disruption feeds and community reports that carry confirmation and expiry; participatory development with self-advocacy organisations, and EN 301 549 from the first line rather than at acceptance testing.
Outcome A documented concept: the data already exists and is openly licensed — the work is in connecting it. Gap analysis against Wheelmap, operator lift-status services and academic OSM routing prototypes shows nobody joins static infrastructure, multi-operator real-time status and community knowledge into one continuous door-to-destination route. Positioned against existing obligations (UN CRPD Art. 9, National Action Plan on Disability 2022–2030, BaFG), with the open points — advisory board, first user research — stated rather than hidden. One building block is already specified in detail: beacon-guided wayfinding for the places where GPS gives up, with the accessibility graph held offline on the device, reports tied to a confirmed beacon so that they carry weight, and the WU Vienna campus as the first pilot area — small enough to survey, public, and mixing indoor and outdoor space.
Accessibility Routing Real-time Data OpenStreetMap Participatory Design

Concept · Ongoing

IntelligentLiving

A home that understands situations instead of waiting for commands, and takes the small everyday decisions off your hands. The goal is not more smart home — it is less for you to think about: no setting things in the morning, no checking whether everything is switched off, no app for every part of the house, no rules for you to maintain.

Question Can a home be intelligent without becoming the next interface that demands your attention — and stay privacy-first in its architecture rather than only in its marketing?
Methods An intelligence layer above existing home automation, separated from it by a deliberate boundary: the layer forms an intent, the house decides locally what follows from it. A language model proposes; it does not act. Where processing happens is decided per class of data rather than once for the whole product, and the system degrades in stages so that a lost connection costs intelligence, not function. Automation is split into doing, coordinating and anticipating, with cost, reach and safety deciding what may happen without confirmation.
Outcome A worked concept covering the context model, the local/remote boundary, and a two-stage concierge — AI for what is digital and clearly ordered, a person where a person is the better answer. Including a room device deliberately built without display, logo or permanent status light, because the technology is meant to disappear rather than announce itself.
Home Intelligence Privacy-first Local Inference Concept Design

fuxiq · In development

Shopping Intelligence Platform

A consumer platform that turns grocery receipts into a household demand profile, then uses that profile to surface offers that are genuinely better for that household, plan shopping trips and show where the money actually goes. The receipt is the hard part: everything downstream depends on the line items being right.

Question Can a household’s own receipts produce a demand profile precise enough to find offers that are genuinely better for that household — and how do you know when an extracted receipt is trustworthy enough to build on?
Methods Austrian receipts carry a fiscal QR code with a cryptographically signed total, which the pipeline treats as a ground-truth oracle instead of trusting the model’s own output. Perspective-corrected cropping and OCR feed a structured extraction; where the extracted total disagrees with the signed one by more than a cent, a second model runs with the signed total injected as a hint. A supervision interface exposes every intermediate stage — crop, decoded code, OCR text, extracted data — so a failure can be attributed to a step rather than to the pipeline as a whole.
Outcome An extraction pipeline with a built-in correctness signal: for each receipt it can state whether the result reconciles against a signed total, rather than reporting a confidence score. Receipt extraction is the phase in progress; the demand profile and offer matching build on it.
Document Extraction LLM Validation OCR Structured Output Consumer Data

Bachelor Thesis.

Grounding medical answers in a human-curated knowledge graph — at WU Vienna.

Title
Reducing Hallucinations in LLM-Based Question Answering through Hybrid Multi-Agent Knowledge Graph Traversal
In Progress · 2026

LLMs can sound confident and be completely wrong. This thesis grounds medical question answering in a graph built from human-curated sources rather than extracted by a model — because a model-built graph puts hallucination into the substrate itself, before a question is ever asked. Sub-agents traverse the complete Wikidata truthy graph in parallel from different entry points, and a main agent selects the evidence the answer is built on. Accuracy and faithfulness are scored separately, so a system that is right for the wrong reasons does not count as a success.

Research Focus

  • Hybrid seeded traversal with parallel sub-agents
  • Accuracy and faithfulness scored separately
  • Human-curated vs. LLM-extracted graph substrates
  • Compared against one-shot prompting, two-step RAG and agentic RAG
